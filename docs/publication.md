# 消息发布时间查证

每条福利的卡片和详情页独立显示消息发布时间；默认时间流仍按首次收录排列。两种时间不能互换，规则核验时间也不会因日期查证而刷新。

本机 GPT 使用与 Hermes 相同的运行配置，为需要查证的福利规划一次真实联网查询，通过既有独立 DDGS 环境搜索，读取官方原文及搜索结果对应的公开页面，再判断日期与具体权益的关联。日期有字面原文支持且通过独立复核才写入正式数据。

- 官方明确发布消息的日期：显示“消息发布：2025年3月12日”。
- 只有年或月依据：显示“消息发布：约2025年3月”，不补成1日或午夜。
- 有日期的报道只能证明权益当时已存在：显示“最晚已于2025年3月存在（发布时间估计）”。这不是最早上线日。
- 已检索但无法核实：显示“消息发布时间：未知”；尚未完成或遇网络故障：显示“待查证”。详情页保留简短原因和可访问的日期依据。

活动开始日、截止日、文档最后更新、版权年份、HTTP Last-Modified 和本站收录时间均不能冒充发布时间。不同套餐版本、不同地区或不同额度的旧消息不能直接用于当前条目。搜索结果的摘要只作为线索，未经实际抓取的摘要不能成为日期证据。日期是公开信息查证结果，不保证找到了互联网最早消息。

## 限额与持久化

`data/publication.json` 默认启用独立日期查证阶段：每小时最多2条福利，每条最多1个 GPT 规划的查询、5条搜索结果和3个页面（含现有官方规则页），两个并发工作任务。每个页面最多1 MiB、42,000个可读字符，总输入有界。它不占用或扩大新信源发现阶段的4查询预算。

`npm run scan:due` 的正式入库结束后执行日期阶段，然后构建静态站点；Vercel 只读取结果，不联网查日期或调用模型。项目维护通过原有 `scan:due` 到期逻辑接入此阶段；GitHub 同步或 Vercel 核对的重试不重复查日期，也不改变本阶段预算、冷却与失败退避。日期阶段失败不回滚已核验福利；扫描报告以 `publication` 单独记录状态，`work/publication-report.json` 保存本机详细计数。发现日期失败不能冒充日期未知。

首次回填或用户明确要求时可运行：

```sh
npm run dates:backfill -- --limit 28
```

这个入口最多30条，只查日期，不触发新信源发现或重新审批福利；共用日期阶段的 PID/token 领取及数据写锁，不抢占活跃任务，也不跳过单条失败退避。定时维护不使用它强行重复搜索。

已完成的 `publication` 判断直接存入正式 `data/offers.json`，随原有 GitHub 同步持久保存。已知日期不会每小时重查；未知结果30天后才重查；网络/模型失败至少60分钟后重试。`work/publication-state.json` 在付费调用前领取预算并记录失败退避，不能为重复搜索手工删除或改时间。

日期补充只修改该条 `publication` 和数据文件更新时间，保留首次收录、规则核验和其他条目；写入前重新读取并比较权益、适用范围及日期快照，保护并发人工更正。人工日期不被自动覆盖。后续规则复核保留同一权益的日期，自动日期所关联的权益/资格/地区发生变化时重新排队，避免套用旧版本日期。

正式数据只含日期值、精度、判断类型、公开依据的短引文/URL、查证时间与模型名。原始搜索、抓取全文、内部错误和凭据留在本机；模型凭据不上传 GitHub 或 Vercel。
